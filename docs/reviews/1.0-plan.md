# rust-webx 1.0 规划（含 rust-dix 0.8 升级）

> 状态：规划稿（2026-11-11）。基于 0.10.0 发布后的仓库状态，并入「rust-dix 0.8 升级」与
> 0.10 遗留待办。执行顺序以文末里程碑 M0–M5 为准。

## 0. 结论摘要

- **rust-dix 0.8.0 已于 2026-11-11 发布**（crates.io `rust-dix` / `rust-dix-macros` 0.8.0，
  `created_at` = 2026-11-11T01:32Z）。本轮用临时分支做了真实编译/测试探针（见 §5）。
- **框架 crates（core / host / webx / spa / build / openapi / macros）在 rust-dix 0.8 下
  无需改源码即可编译**；框架测试仅 **1 个语义测试失败**（严格 scope 校验导致 root 解析
  Scoped 返回 `Err`），说明升级风险集中在 **DI 语义与生命周期**，不在 API 形状。
- **真正阻塞是外部依赖：`rust-ef`**。`rust-ef` 2.0.1（最新，2026-11-09）依赖
  `rust-dix = "0.7"`，GitHub main 也仍是 `"0.7"`；因此 docbit/dmbit 与用户侧
  `add_dbcontext` 扩展在新版下不可用（探针中 `docbit-host` 的 `scope_smoke` 示例报
  `E0599: no method named add_dbcontext`）。`Cargo.lock` 会同时出现 rust-dix 0.7.0 与 0.8.0。
- **建议**：把 rust-dix 0.8 升级与 0.10 遗留兼容层删除合并为 **rust-webx 1.0.0** 一次性
  breaking 发布；**M0 门禁 = rust-ef 发布一个依赖 rust-dix 0.8 的版本**（推荐同组织内推动
  rust-ef 2.1.0）。在 M0 完成前，1.0 只做分支预研，不发版。

## 1. rust-dix 0.8 变更摘要（官方 CHANGELOG）

来源：crate 内 README + GitHub `Rust-Framework/rust-dix` CHANGELOG（0.8.0 段，中英双语）。

### 1.1 Breaking / 语义变化

| 变更 | 0.7.x 行为 | 0.8.0 行为 | 对 rust-webx 的关注点 |
|---|---|---|---|
| 单服务解析顺序 | 实际「先注册优先」（与部分文档不符） | **MEDI 风格「后注册优先」**：`get` / `get_optional` / `get_owned` / `get_keyed*` / `get_async` | 框架内置默认注册（localizer、endpoint catalog、mediator、middleware、hosted、pipeline）要改用 `try_add*`，保证用户注册不会被框架后注册覆盖 |
| `get_all` | 含 keyed + unkeyed | **只含非 keyed**；keyed 用新增 `get_all_keyed::<T>()` | webx 用 `get_all` 收集 `dyn IMiddleware` / `dyn IHostedService` / `dyn IPipelineBehavior<..>` / `dyn IEventHandler<T>`；目前框架不注册 keyed，但需在文档说明「keyed 实现不会被 get_all 收集」 |
| 严格 scope 校验 | root 可直接解析 Scoped（root 内缓存） | **默认严格**：root 解析 Scoped → `Err(RdiError::ScopedFromRootProvider)`；`get_optional`/`get_all`/`try_*` 视为不可解析；`get_owned`/`try_get_owned` 例外（归调用方、不缓存），但其构造函数内的 Scoped 依赖仍校验 | 探针唯一失败点；`dispatch_provider()` 是 root provider，用户/测试里 `dispatch_provider().get::<Scoped>()` 会由 Ok 变 Err。需要改文档/测试，并决定是否提供 lenient 逃生门 |
| dispose 契约 | 无 Provider 级 dispose | `Scope` 跟踪 Scoped 实例，`Drop`/`dispose()` 逆序释放 + 逆序执行 cleanup；新增 `ServiceProvider::dispose()`；dispose 后解析返回 `ProviderDisposed` / `ScopeDisposed`；两者幂等 | rust-webx 目前从不调用 `provider.dispose()`；应在 Host 停机序列补上，并验证 singleton 释放顺序、dispose 后 dispatch 行为 |
| `RdiError` | 可穷举匹配 | **`#[non_exhaustive]`**，新增 `ScopedFromRootProvider` / `ProviderDisposed` / `ScopeDisposed` | webx 代码没有穷举匹配（已 grep），暂无编译影响；对外错误映射文档需补新变体 |

### 1.2 新增能力（1.0 可评估采纳）

- `ServiceProviderOptions`（`#[non_exhaustive]`，`validate_scopes`）、`build_with` / `build_async_with`；
  `lenient()` 恢复 0.7 的 root-scope 行为。
- `ServiceProvider::dispose()` / `Scope::dispose()`；`is_registered::<T>()` / `is_registered_keyed`；
  `get_all_keyed::<T>()`；`IServiceResolver` 新增 `get_all_keyed_any` / `try_get_any_result` /
  `try_get_keyed_any_result` / `get_all_any_result`。
- `get_async` / `get_keyed_async` 对同步注册服务回退同步路径；async Scoped/Transient 递归检测防止死锁。
- `build_async` 按注册顺序初始化 async singleton；`async_*` 注册必须用 `build_async`。
- `IProvider` 统一 DI 接口（给不直接依赖 rust-dix 的外部模块）；named services（跨 DLL）；
  `ServiceProviderWrapper` 分层容器（插件隔离）。
- Macros：`#[inject]` 放在 trait impl 上即可自动按 trait 注册（替代旧 `as = dyn Trait` 语法）；
  `#[inject]` on struct 注册具体类型、`#[derive(Inject)]` 只生成构造器；`from_injected()` 收集。
- 0.7.1 起：`#[inject(provider)]` / `Arc<dyn ScopeFactory>` 可在 eager singleton 构造期注入；
  singleton 内推荐 `Arc<dyn ScopeFactory>`（弱引用，避免 Arc 环）。0.8 的 `build()` 按注册顺序
  eager 创建 singleton（顺序确定，构造/释放可复现）。

## 2. rust-webx 现状盘点（rust-dix 使用面）

全仓 `rust_dix` 引用约 56 处；关键位置：

| 位置 | 用法 | 升级动作 |
|---|---|---|
| `crates/host/src/server.rs:540` | `svc.build()` 构建 root provider | 改 `build_with(...)`：默认 strict，新增 `HostBuilder::lenient_scope_validation()` 显式逃生门（映射 `ServiceProviderOptions::lenient()`） |
| `crates/host/src/server.rs:532-538` | `instance(health_registry)`、`singleton::<dyn IEndpointCatalog>`、`singleton::<dyn IStringLocalizer>` | 这些是框架默认实现；改 `try_add*` 以保持「用户先注册的覆盖生效」语义；`IEndpointCatalog`/localizer 的覆盖规则写进文档 |

| `crates/webx/src/lib.rs` | `pub use rust_dix::{inject, ScopeFactory}` + `module`/`Inject` | 继续 re-export；新增 `ServiceProviderOptions`（若暴露 lenient 选项）或保持封装；宏用法文档从 `as = dyn` 更新为「impl 上 #[inject]」 |
| `docbit/dmbit` | 大量 rust-ef 实体/`add_dbcontext`/`DbContext` | **受 rust-ef 阻塞**（见 §3 M0）；docbit 自封装的 `add_docbit_db`（`docbit/host/src/startup/extensions/service_collection.rs`）可先行适配 0.8，`docbit/host/examples/scope_smoke.rs:31` 直接调 `add_dbcontext` 需等 rust-ef |
| `Cargo.toml:53-54` | `rust-dix = "0.7"`、`rust-dix-macros = "0.7"` | 升 `"0.8"`；注释 `rust-ef ORM (rust-dix 0.7 integration ...)` 同步更新 |
| 测试 | host 测试直接 `ServiceCollection` + `DispatchRuntime`；`mediator_test` 的 `TestMediator` 已用 DispatchRuntime 包裹 | 新增 strict/lenient、try_add 覆盖、last-wins、dispose、root-scope 错误语义回归 |

已确认无影响的点：
- 无 `RdiError` 穷举匹配（新 `#[non_exhaustive]` 不破坏编译）；
- 无 `as = dyn` 用法；
- `ScopeFactory`/`IServiceResolver` 仍可用（探针编译通过）。

## 3. 需要同步升级迭代的内容（P0 / P1 / P2）

### P0（1.0 阻塞）

1. **rust-ef 0.8 兼容版本（外部 M0）**
   - 现状：rust-ef 2.0.1 依赖 `rust-dix = "0.7"`；GitHub main 未迁移（本轮 fetched `crates/core/Cargo.toml` 仍 `0.7`）。
   - 影响：`add_dbcontext` / `add_dbcontext_keyed` 扩展 trait 绑定 0.7 的 `ServiceCollection`；
     双版本 rust-dix 并存时容器类型不互通，docbit/dmbit 与用户文档路径无法工作。
   - 推进方式（推荐）：同组织内推动 rust-ef 2.1.0（改动集中在 `crates/core/src/di.rs`：
     dep bump + 严格 scope 文档/示例 + `create_scope()`→`provider.scope()` 措辞 + root-scope 测试调整；
     `add_dbcontext` 的 scoped 注册本身无需改）。
   - 验收：`cargo tree -i rust-dix` 只剩 0.8；docbit/dmbit 全部 target 编译通过；rust-ef `di` 相关测试在严格 scope 下通过。
2. **Host DI 构建策略**
   - `HostBuilder::try_build()` 内部改 `build_with(ServiceProviderOptions::default())`（strict）；
     新增 `HostBuilder::lenient_scope_validation()`（仅迁移期使用，文档标注 deprecated 计划）。
   - `Error::Di` 文案兼容新 `RdiError` 变体；`ScopedFromRootProvider` 给出可操作提示（`provider.scope()` / `dispatch_provider().get_owned()`）。
3. **root-scope 语义适配**
   - 更新 `dispatch_runtime` 文档与 `scope_provider_does_not_leak_outside_run_in_scope` 测试：
     root `get::<Scoped>` = Err；`get_owned` 仍可（例外）；`run_in_scope` 内行为不变。
   - `dispatch_provider()` / `host.provider()` 文档补充：推荐 `run_in_scope` 或 `get_owned`，root `get::<Scoped>` 不再支持。
4. **框架默认注册改 `try_add*`**（避免 0.8 last-wins 反转覆盖语义）
   - `add_mediator`、`add_middleware`、`add_hosted_service`、`add_typed_pipeline*`、Host 的 localizer/endpoint catalog/health registry。
   - 新增回归：先注册用户实现 → 再走 `Host::builder()` 默认注册 → 解析结果必须是用户实现（0.7 语义保持）。
5. **生命周期：provider.dispose()**
   - Host 停机顺序：停止接受请求 → 停 hosted services → 等连接 drain → **`provider.dispose()`**。
   - 测试：disposable singleton 逆序释放；dispose 后 `dispatch_provider()`/`get` 返回 `ProviderDisposed`；Host 重复 shutdown 幂等。
6. **依赖与锁文件**
   - workspace `rust-dix = "0.8"`、`rust-dix-macros = "0.8"`；rust-ef 升级后 `Cargo.lock` 只留 0.8。
   - `crates/*/Cargo.toml` 若有直接依赖同步；CI 增加 `cargo tree -d`/`cargo tree -i rust-dix` 检查防双版本。

### P1（1.0 建议纳入）

9. **文档 / 技能**

## 6. 决策记录

- **D1：0.8 升级放进 1.0 而非 0.10.x。** 严格 scope 校验、last-wins、`get_all`/dispose 语义都是
  对用户可见的 breaking，必须 minor/major 承载；1.0 是冻结 API 前的最后一次 breaking 窗口。
- **D2：默认采用 strict scope 校验 + 显式 lenient 逃生门。** 对齐 MEDI/ASP.NET Core 开发默认（`ValidateScopes=true`），
  减少「root 解析 Scoped 变成 root 单例」的隐性 bug；同时给迁移期一个显式开关。
- **D3：1.0 以 rust-ef 0.8 兼容版本为发布门禁。** 不发布「框架 1.0 + 示例仍锁 0.7」的组合：
  双版本 rust-dix 会让 `add_dbcontext` 等集成路径失效，且与公开文档/技能不一致。
- **D4：不做双版本兼容层。** rust-dix 0.7/0.8 的容器类型互不兼容，兼容层成本高于收益；
  用 M0 门禁替代。
